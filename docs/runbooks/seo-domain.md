# Runbook: public domain, canonical URLs, sitemap, robots.txt and signup funnel

Task SE-02, audit defect A8-02 (P0), decision D3: the public domain is configurable and **no domain is written in
code** (no default in `appsettings.json`, `vercel.json` or the sources). The code is in place; the product owner
chooses the domain, sets the variables of section 2 and follows sections 3 and 4.

Task SE-01, audit defects A8-04, A8-05, A8-06, A8-21 and R-09: a page is public only with a text a person read and
approved in the admin dashboard; section 7 describes the review flow, the audit and what the migration withdrew.

Task SE-03, audit defect A8-03 (P0): the CTA of the SEO pages leads to `/signup`, which opens the Auth0 **signup**
screen in one click and records where the signup came from (UTM parameters, comune, landing page, referrer host).
Section 6 describes the funnel, the Auth0 setting it needs and how to read the attributions.

### Why a function for the sitemap and a build-time robots.txt

- A plain rewrite in `vercel.json` to the backend would need the API domain written in the file (against D3), and the
  same file serves the preview deployments (test API) and production (production API). The function reads
  `VITE_API_BASE_URL` of its own environment at runtime.
- A sitemap generated at build time would be stale until the next frontend deploy (pages are published from the admin,
  on the backend) and would make every build depend on the API being up. The function is always current and the CDN
  cache keeps the load on the API negligible.
- `robots.txt` must never depend on the API: Google treats a `5xx` on `robots.txt` as "do not crawl the site". Built
  from `VERCEL_ENV`, it needs no variable to keep preview and test deployments out of the index.

## 1. Choose the public domain

The domain is a product decision (not taken in code). Once chosen:

1. Vercel → project → **Settings → Domains**: add it and assign it to **Production** (branch `main`). Follow the DNS
   records Vercel shows, wait for the certificate.
2. Decide what the other names do (e.g. the apex redirecting to `www`, or the old `*.vercel.app` production URL):
   Vercel → Domains → **Redirect to** the chosen domain, so only one host serves the pages.

## 2. Variables

Set them **before** the release reaches `main`: the production API does not start without `App__PublicSiteBaseUrl`
(the value that used to be committed in `appsettings.json` is gone), and the production web app build fails without
`VITE_PUBLIC_SITE_URL`.

Railway (backend), per environment:

| Variable | test | production |
|---|---|---|
| `App__PublicSiteBaseUrl` | `https://<web app URL of the develop deployment>` | `https://<public domain>` |
| `Seo__PublicBaseUrl` | unset | unset (or exactly the same value as `App__PublicSiteBaseUrl`) |
| `Cors__AllowedOrigins` | other web app origins of the environment, if any | other origins, if any (the public domain is already allowed) |

Optional, Railway, per environment (SE-03):

| Variable | When | Value |
|---|---|---|
| `PublicHost__BaseDomain` | only if hosts may publish their booking site on a CasaZen subdomain | the domain whose wildcard record `*.<domain>` points to the Vercel project (e.g. `sites.<your domain>`); no scheme, no dots at the ends. Unset = subdomain mode off |
| `Legal__Documents__Privacy__DocumentUrl`, `Legal__Documents__Tos__DocumentUrl` | when the product owner publishes the CasaZen Privacy and Terms | absolute https URL of each document; the public footer links them |

Vercel (frontend) → Settings → Environment Variables:

| Variable | Preview (develop / PR) | Production (main) |
|---|---|---|
| `VITE_PUBLIC_SITE_URL` | not needed (robots.txt is `Disallow: /`) | `https://<public domain>`, **the same value** as Railway production `App__PublicSiteBaseUrl`, scheme and host only |
| `VITE_API_BASE_URL` | already set (test API) | already set (production API); the sitemap function also reads it at runtime |

Vercel → Settings → Environment Variables → **Automatically expose System Environment Variables** must stay on (the
default): the build reads `VERCEL_ENV` from it. After changing a variable, redeploy (Deployments → Redeploy).

## 3. Checks after a deploy

```bash
SITE=https://<public domain>
API=https://<railway url of production>

# robots.txt: text, indexing allowed, sitemap on the public domain
curl -sS -o /dev/null -w "%{http_code} %{content_type}\n" "$SITE/robots.txt"   # 200 text/plain…
curl -sS "$SITE/robots.txt"          # User-agent: * / Allow: / / Sitemap: https://<public domain>/sitemap.xml

# sitemap.xml: XML, cached, every URL on the public domain
curl -sS -D - -o /tmp/sitemap.xml "$SITE/sitemap.xml" | grep -iE "^HTTP|^content-type|^cache-control"
grep -o "<loc>[^<]*</loc>" /tmp/sitemap.xml | grep -v "<loc>$SITE/" && echo "WRONG HOST" || echo "all URLs on $SITE"

# canonical of a published page = the same URL on the public domain
curl -sS "$API/api/public/content" | grep -o '"canonicalUrl":"[^"]*"'
curl -sS "$API/api/public/content/affitti-brevi/<region>/<comune>" | grep -o '"canonicalUrl":"[^"]*"'

# CORS: the public domain may call the API (answer contains access-control-allow-origin: $SITE)
curl -si -X OPTIONS "$API/api/public/content" -H "Origin: $SITE" \
  -H "Access-Control-Request-Method: GET" | grep -i "^access-control-allow-origin"
```

In the browser: open `$SITE/p/affitti-brevi` (list of the published pages, or "no guides published yet"), follow a
link, check the footer link "Guide per gli host" on a `/p/…` page.

Preview / test deployment: `curl -sS https://<develop deployment URL>/robots.txt` must print `Disallow: /`. If Vercel
Deployment Protection is on, open the URL in a logged-in browser instead.

## 4. Google Search Console

1. <https://search.google.com/search-console> → **Add property** → **Domain** → the public domain (covers `http`,
   `https` and every subdomain). Verify with the DNS **TXT** record Google shows, at the DNS provider of the domain.
2. **Sitemaps** → submit `https://<public domain>/sitemap.xml`. The status must become **Success**; "Discovered
   pages" equals the number of `<loc>` of section 3.
3. **URL inspection** → `https://<public domain>/p/affitti-brevi` → **Test live URL**: the rendered page shows the
   list, and "User-declared canonical" is the same URL. Repeat for one guide.
4. Never add the preview or test deployments: they are `Disallow: /`.
5. If the old `…/sitemap-compliance.xml` of the API host was ever submitted, remove it (Sitemaps → ⋮ → Remove).

## 5. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Railway deploy log: `App__PublicSiteBaseUrl is missing or invalid` | variable not set (or not an absolute https URL) | set it (section 2), Railway keeps the previous deployment meanwhile |
| Railway deploy log: `Seo__PublicBaseUrl differs from App__PublicSiteBaseUrl` | both set with different values | delete `Seo__PublicBaseUrl` |
| Vercel build log: `VITE_PUBLIC_SITE_URL is missing` / `must use https` / `must be the site root` | production variable missing or with a path | set `https://<public domain>` on Production, redeploy |
| `/sitemap.xml` answers `503` | API down, or `VITE_API_BASE_URL` wrong on that Vercel environment | `curl "$API/api/public/sitemap.xml"`; Vercel → Deployments → the deployment → **Functions** / logs show `sitemap.xml unavailable: …` |
| Sitemap URLs on another host | `App__PublicSiteBaseUrl` of that Railway environment is not the public domain | fix it; the CDN refreshes the sitemap within an hour (or redeploy the web app) |
| Production `robots.txt` says `Disallow: /` | the build did not see `VERCEL_ENV=production` | turn on "Automatically expose System Environment Variables", redeploy |
| Sitemap with no `<url>` / hub empty | no page approved yet (section 7); calculators also need a tourist tax rate in force | review and approve pages from the SEO admin; rates: [`tourist-tax-rates.md`](tourist-tax-rates.md) |
| The web app on the public domain gets CORS errors | the domain in the browser is not the one in `App__PublicSiteBaseUrl` (e.g. apex vs `www`) | redirect the other names to the chosen domain (section 1), or add the extra origin to `Cors__AllowedOrigins` |

## 6. Signup funnel and attribution (SE-03)

### How it works

1. **Landing.** The first public page of a visit (`/p/…`, `/book/…`, `/search`, …) records in the tab's
   `sessionStorage` its path, the host of the referrer (only the host is kept, never the full URL) and its UTM
   parameters.
2. **CTA.** Every SEO page shows "Pubblica la tua casa". The backend builds the link on `App__PublicSiteBaseUrl`:
   `https://<public domain>/signup?comune=<slug>&utm_source=seo-compliance&utm_medium=cta&utm_content=<compliance-guide|tourist-tax-calc>`.
   When the visit has UTM parameters of its own (e.g. a newsletter link to the guide), the web app replaces the whole
   UTM set with them; the comune stays. It is a plain link: the public pages run without Auth0 and the browser loads
   `/signup` with it. The "Verifica conformità" CTA is removed: `/tools/verifica-conformita` has no spec.
3. **`/signup`.** Stores the attribution in `localStorage` (`cz-signup-attribution`, forgotten after 30 days) and calls
   Auth0 `loginWithRedirect` with `screen_hint=signup`: the visitor lands on the Auth0 signup screen, no intermediate
   login page. An account already signed in goes to its area and its attribution is forgotten. The button on the page
   restarts the signup (browser Back, blocked redirect).
4. **After the first onboarding** (the org is created) the web app sends
   `POST /api/users/me/signup-attribution`. The backend stores **one row per org** (`SignupAttributions`, unique
   `OrgId`): the first attribution wins, retries and parallel calls answer `recorded: false`. If the call fails with a
   network or 5xx error the web app retries on the next page load; a 4xx is never retried. An account that was already
   onboarded when it came through `/signup` (it signed in from the signup screen) sends nothing.

Stored values (no personal data): `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content` (max 100
characters: letters, digits, space and `- _ . ~ + | : , / ( ) !`; never `@`), the ISTAT code of the comune (from the slug
or code of a comune CasaZen knows), the landing **path** (max 200, no query string) and the referrer **host** (max 253).
A value outside these rules is **refused, not truncated**: 400 `validation_error` (422
`signup_attribution_unknown_comune` for an unknown comune) and nothing is stored; the web app drops such values already
when it reads the URL, so a stray parameter does not cost the rest of the attribution. Before the onboarding the call
answers 422 `signup_attribution_onboarding_required`.

Anonymous visitors on public paths are never sent to the login: an unknown address shows the public 404 (it used to go
to `/` and then to `/login`), and a link from a public page to a page that needs Auth0 (`/signup`, `/login`, the app)
reloads that page with Auth0 instead of showing a login page that needed a second click.

### Auth0 setting (product owner)

`screen_hint=signup` opens the signup screen of **Universal Login** (the current experience). Auth0 Dashboard:

1. **Branding → Universal Login**: the experience must be the current Universal Login (with the Classic experience and a
   custom page the hint is ignored and the login screen is shown).
2. **Authentication → Database → <connection of the app> → Settings**: "Disable Sign Ups" must be **off**.
3. **Applications → <SPA> → Settings**: the "Allowed Callback URLs" already contain the web app origin (the signup
   returns there like the login, see [`auth0.md`](auth0.md)).

### Checks

```bash
SITE=https://<public domain>
API=https://<railway url of the environment>

# CTA of a published page: /signup on the public domain with the comune
curl -sS "$API/api/public/content/affitti-brevi/<region>/<comune>" | grep -o '"signupUrl":"[^"]*"'
# expected: "signupUrl":"https://<public domain>/signup?comune=<comune>&utm_source=seo-compliance&utm_medium=cta&utm_content=compliance-guide"

# unknown address: the SPA answers (Vercel) and shows the public 404 in the browser, no redirect to /login
curl -sS -o /dev/null -w "%{http_code}\n" "$SITE/pagina-che-non-esiste"   # 200 (index.html), page "Pagina non trovata"
```

In the browser (private window): open a guide, click "Pubblica la tua casa": the Auth0 **signup** form opens at once.
Sign up with a test address, complete the onboarding, then, as platform admin:

```bash
curl -sS -H "Authorization: Bearer $ADMIN_ACCESS_TOKEN" "$API/api/admin/signup-attributions?days=1"
# items[0]: orgId of the new org, utmSource "seo-compliance", comuneCode "<ISTAT code>", landingPath "/p/…"
```

`GET /api/admin/signup-attributions` (AdminOnly): newest first, `days` (default 30, max 3660), `comuneCode` (ISTAT),
`page`, `pageSize` (max 100). The dashboard widget (top comuni) is task SE-04.

### Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| The CTA opens the Auth0 **login** form | Classic Universal Login, or sign-ups disabled on the connection | Auth0 setting above |
| `signupUrl` is a relative `/signup?…` | `App__PublicSiteBaseUrl` not set (only possible outside Production) | section 2 |
| No row after a test signup | the account already existed (it signed in from the signup screen), the storage of the browser is blocked, or the call failed: it is retried at the next page load | check the network tab for `POST /users/me/signup-attribution` |
| Domain settings: "I sottodomini CasaZen non sono ancora disponibili" | `PublicHost__BaseDomain` not set | set it (section 2) and the wildcard DNS record, or use the path / custom domain |

## 7. Legal review and publication (SE-01)

Defects A8-04 (the legal review was an automatic stamp), A8-05 (a regeneration republished text nobody had read), A8-06
(stub, empty or uncontrolled text published), A8-21 (admin UX), R-09 (pages with the stub sentence
"Milano: contenuto generato per affitti brevi, CIN e tassa di soggiorno." in production).

### The flow

1. **Generation creates drafts only.** The bootstrap, "Genera tutti" (`POST /api/admin/seo/generate`) and the monthly
   refresh (a tourist tax rate changed) store a new **draft revision**. Nothing is approved automatically: the
   `Seo:AutoApproveAfterBootstrap` option, the `autoApproveCounsel` flag of `generate` and the "Approva tutte" button and
   endpoint (`POST /api/admin/seo/approve-all-drafts`) are gone. A Hangfire job queued before SE-01 with the old flag
   still runs, ignores it and logs a warning.
2. **Output checks** (`SeoGeneratedContent`). Each revision has a `ContentStatus`; only `Generated` can be approved:

   | `ContentStatus` | When | Body stored |
   |---|---|---|
   | `Generated` | a configured provider answered with an HTML fragment of the FD-15 allowlist, with `<h2>` sections and `<p>` paragraphs, at least 600 characters of text, no markdown | sanitized text |
   | `AiProviderNotConfigured` | `Ai:Provider` is `Stub` (the default) or DeepSeek has no `Ai__ApiKey` | empty |
   | `EmptyOutput` | the provider answered with nothing (or only markup) | empty |
   | `InvalidOutput` | markdown, a chat reply ("Sembra che tu abbia fornito…"), no sections, too short | sanitized answer, for the admin to see |
   | `Placeholder` | stub text found by the SE-01 migration | unchanged |

   The admin list shows these as "Contenuto non generato: …". A page left in one of them is generated again by the next
   "Genera tutti" (also without "force") once a provider is configured.
3. **Prompt** (`SeoContentPrompt`, version stored with each revision, currently `seo-it-2026-09-v1`): Italian, only the
   HTML tags of the allowlist, the sections to write (CIN, Alloggiati Web, imposta di soggiorno, Fonti ufficiali for the
   guide; imposta, calcolo, esenzioni, fonti for the tourist tax page), 300-600 words, no legal or tax advice, and **only
   the facts and sources listed in the prompt**: the CIN and Alloggiati facts verified in
   `.claude/context/regulations/cin.md` and `alloggiati.md` with their official URLs, and the tourist tax rates of the
   comune in force today with their `SourceUrl` (https only). Without a rate the prompt says there is no verified rate and
   no amount may be written. A new prompt version makes "Genera tutti" regenerate every page.
4. **Review** (admin → SEO → "Rivedi"): the text waiting for approval next to the text published now, both sanitized as
   the public page shows them, and the review history. "Approva e pubblica" needs the confirmation checkbox ("revisione
   legale"; for the first 100 pages, `CounselRequired`, the backend refuses without it: 422 `seo_counsel_required`) and
   takes an optional note (max 1000 characters). The approval names the revision that was read: if a newer revision
   arrived meanwhile the API answers 409 `seo_revision_outdated` and nothing is published; a "not generated" revision
   answers 422 `seo_revision_not_publishable`.
5. **What the public sees**: the page, the hub, the sitemap and the link of the activation wizard use **only**
   `SeoContentPages.PublishedRevisionId`. A regeneration of a published page leaves the approved text online; the list
   shows "Pubblicata · nuova revisione da approvare" until the new text is approved. The rates table and the calculator of
   the page are live data (`TouristTaxRate`), so after a rate change the approved text may mention the old amount until the
   new revision is approved: review those first. A page without an approved revision answers 404 and is not in the
   sitemap, **in every environment** (Development, Testing and Staging used to serve drafts: read them in the admin).
6. **"Ritira"** (withdraw, with confirmation and an optional reason): the page goes back to draft and leaves the public
   site, the hub and the sitemap at once (the Vercel CDN may keep the old `/sitemap.xml` up to 1 hour).

`LegalReviewStatus` now describes the **latest** revision: `Reviewed` = it is the published one, `Draft` = it waits for a
review (the page may still be published with an older text). The filter "Da revisionare" of the dashboard lists them.

### Audit

Every approval and withdrawal is a row of `SeoContentReviewEvents` (append-only): page, revision (the approved one, or the
one that was published when the page was withdrawn), `Action` (`Approved` / `Withdrawn`), `ActorUserId` (Auth0 subject of
the admin, `system:SE-01` for the migration), `OccurredAt` (UTC), `CounselApproved`, `Note`. The review dialog shows it;
in SQL (Supabase SQL editor, schema of the environment):

```sql
SELECT p."Slug", e."Action", e."ActorUserId", e."OccurredAt", e."CounselApproved", e."Note", e."RevisionId"
FROM "SeoContentReviewEvents" e
JOIN "SeoContentPages" p ON p."Id" = e."PageId"
ORDER BY e."OccurredAt" DESC;
```

### What the migration `SeoRevisionReview` withdrew

On deploy the migration:

1. marks as `Placeholder` every revision holding the stub sentence (`…: contenuto generato per affitti brevi, CIN e tassa
   di soggiorno.`) and as `EmptyOutput` every revision without text;
2. puts back to **draft** every page that was published (`LegalReviewStatus = Reviewed`) with such a latest revision or
   with no revision at all, and writes a `Withdrawn` audit row by `system:SE-01` whose note says why ("testo segnaposto
   del provider Stub", "testo vuoto", "senza alcun testo");
3. keeps published the other reviewed pages, with the revision the public was seeing (their latest) as
   `PublishedRevisionId`.

With the default provider (no `Ai__*` variables) every bootstrap page was stub text (R-09), so on such an environment
**all** SEO pages leave the public site and the sitemap until a provider is configured and each text is approved. The
list of what was withdrawn:

```sql
SELECT p."Slug", e."Note", e."OccurredAt"
FROM "SeoContentReviewEvents" e
JOIN "SeoContentPages" p ON p."Id" = e."PageId"
WHERE e."ActorUserId" = 'system:SE-01'
ORDER BY p."Slug";
```

Pages that stayed published had real text but were approved before the audit existed (possibly by the old automatic
bootstrap): they show no approval in the history. Open them with "Rivedi" and use "Ritira" for any text that was never
reviewed by a person. Down-migrating does not publish the withdrawn pages again.

### Railway variables (product owner)

| Variable | Action |
|---|---|
| `Seo__AutoApproveAfterBootstrap` | delete it if set: it is no longer read |
| `Seo__BootstrapOnStartup` | may stay `true` (default): the first start creates drafts only. With the stub provider they are "contenuto non generato" drafts, generated again by "Genera tutti" once `Ai__*` is configured ([`ai.md`](ai.md)) |

### Checks after the deploy

1. Admin → SEO: no "Approva tutte"; every page shows its publication state and the state of its latest revision; the
   pages withdrawn by the migration show "Ritirata da system:SE-01" in "Rivedi".
2. `curl -sS "$API/api/public/sitemap.xml"`: only pages approved by a person (none right after the migration on an
   environment with the stub provider).
3. With a provider configured: "Genera tutti" → the texts appear as "Testo generato, da revisionare", the public page of
   a new comune answers 404 until "Approva e pubblica"; after the approval it answers 200 and the sitemap lists it;
   "Ritira" removes it again.

## Out of scope

- The `/p/*` pages are rendered in the browser (no prerender): `og:url`, JSON-LD, `noindex` on "not found" pages and
  the sitemaps of the hosts' booking sites are task BK-15 (A8-09, A8-29).
- `GET /api/public/sitemap.xml` also answers on the API host (the function needs it); it is declared nowhere.
